## 1. Project & Role 2 Overview

In a Proof-of-Stake (PoS) consensus protocol, traditional leader selection relies solely on economic stake ($\text{Weight}_v = \text{Stake}_v$). While simple, stake-only selection permits high-stake malicious or faulty nodes to propose and validate blocks with high probability, compromising network throughput and security.

This project introduces **ML-Based Trust-Aware Validator Selection**, replacing the naive stake formula with a joint trust-weighted selection metric:

$$\text{Selection Weight}_v = \text{Stake}_v \times \text{Trust}_v$$

Where:
- $\text{Stake}_v$ is the validator's economic capital deposited in the consensus protocol.
- $\text{Trust}_v \in [0.0, 1.0]$ is an empirical, non-linear machine learning trust score estimated from the validator's historical operational behavior.

## 3. What the ML Model Does

The core engine of Role 2 is an authentic, trained scikit-learn `RandomForestClassifier`:
- It accepts 5 observable validator behavioral metrics from consensus telemetry.
- It outputs continuous class probabilities via `.predict_proba(X)`.
- The **Trust Score** is defined strictly as the model's estimated probability that the validator belongs to the `HONEST` class:

$$\text{Trust Score} = P(\text{HONEST}) = \text{model.predict\_proba}(X)[:, \text{honest\_class\_index}]$$

- **No Manual Weights:** The previous heuristic formula (`0.25*verification_correct + 0.25*transaction_outcome + 0.20*(1-suspicious_flag) + 0.15*response_time_score + 0.15*uptime`) has been completely removed. The Trust Score is 100% generated by the machine learning model.

## 5. Excluded Fields (Data Leakage Wall)

To guarantee model generalization and prevent methodological errors:
- **`true_label`**: Strictly excluded from model inputs. Reserved exclusively for training targets and post-hoc evaluation.
- **`validator_id`**: Strictly excluded from model inputs. The model evaluates *behavioral telemetry*, not node identities, preventing ID memorization.
- **`transaction_id`**: Strictly excluded from model inputs. It is an arbitrary temporal counter used solely for temporal filtering.
- **`stake`**: Strictly excluded from model inputs. Economic stake is reserved exclusively for Role 3/4's selection weighting formula ($\text{Stake} \times \text{Trust}$).

## 7. How Trust Score is Calculated

### Single Transaction Scoring
When a single transaction observation dictionary or row is provided:
1. A 1-row DataFrame $X$ is formed with the 5 feature columns in exact order.
2. `probabilities = model.predict_proba(X)` is executed.
3. The float probability for class `1` is extracted: `trust_score = float(probabilities[0, 1])`.

### Multi-Transaction Historical Log Scoring (Prediction Averaging)
The Random Forest was trained on individual, row-level transaction records. When downstream roles supply a history log of past transactions (e.g., DataFrame or list of dicts over $k$ rounds):
- Each transaction row is evaluated individually through the Random Forest model to compute $P(\text{HONEST} \mid \text{tx}_i)$.
- The cumulative validator trust score is the arithmetic mean of these honesty probabilities:

$$\text{Trust}(v) = \frac{1}{k} \sum_{i=1}^k P(\text{HONEST} \mid \text{tx}_i)$$

- **Representation Integrity:** Raw binary flags (`verification_correct`, `suspicious_flag`, `transaction_outcome`) are **never averaged into continuous fractions prior to tree traversal**. Every transaction is scored against the exact tree splits learned during training.

---

## 8. Cold-Start Policy Behavior

When a newly joined validator enters the network with **no prior transaction history**:
- **Cold-Start Trust Score:** **`0.80`**
- **Operational Tier:** **`NORMAL / MONITOR`**
- **Principle:** `0.80` is a **deterministic protocol policy fallback**, NOT an ML model output. It provides new nodes an initial opportunity to propose blocks while keeping them subject to rapid downgrading if they commit Byzantine faults.

---

## 9. Temporal Safety & Causality Enforcement

In a consensus simulation, evaluating a validator at round $T$ must never use information from round $T$ or future rounds $T+1, \dots$:
- The `get_trust_score()` API accepts an optional parameter: `current_transaction_id=T`.
- When provided, any historical record with $\text{transaction\_id} \ge T$ is **strictly filtered out** prior to scoring.
- If no records exist strictly before round $T$ (e.g., at round 1), the function cleanly returns the cold-start fallback **`0.80`**.
- `transaction_id` is used solely as a temporal filter and is **never** passed into feature matrix $X$.

>    Role 2 returns a single continuous float:
>    $$\text{Trust}_v \in [0.0, 1.0]$$

>
> 4. **Downstream Selection Weighting Formula:**  
>    Role 3/4 computes the consensus proposal probability:
>    $$\text{Weight}_v = \text{Stake}_v \times \text{Trust}_v$$
>    $$\text{Probability}_v = \frac{\text{Weight}_v}{\sum_{j=1}^N \text{Weight}_j}$$
>
> 5. **Leader Selection:**  
>    Role 2 does **NOT** select the winning validator. Selection is the sole responsibility of Role 3/4.

## 16. Important Limitations & Operational Notes

1. **Synthetic Telemetry Characteristics:** In this synthetic dataset, `uptime` (55.58%) and `response_time_ms` (37.22%) drive ~92.8% of Random Forest Gini importance. In production blockchain testnets, adversarial nodes may artificially maintain high uptime while committing Byzantine double-signing, necessitating protocol-level equivocation slash signals.
2. **Cold-Start Grace Window:** Newly registered nodes begin at `0.80` (`NORMAL / MONITOR`). A malicious node joining under a new identity will receive this baseline score until its first faulty transactions are observed by peer validators.
